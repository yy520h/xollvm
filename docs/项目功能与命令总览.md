# XOLLVM 项目功能与命令总览

本文档说明当前源码的实际行为、配置方法、生效范围、组合限制和验收命令。参数速查见同目录 `obf_annotations.h`；默认值以 `include/llvm/Transforms/Obfuscator/ObfuscationConfig.h` 及各 Pass 的配置展开为准。

## 先读：保护范围与“已经生效”的判定

1. **这是源码/LLVM IR 混淆工具链，VM 是函数级虚拟机，不是把整个 ELF 的所有代码装进统一解释器的全程序 VM 壳。** 普通原生函数执行时，不会持续“恢复 VM 壳”。被保护函数调用的外部库也不会自动变成 VM 字节码。
2. **注解是请求，不是生效证明。** 不支持的 IR、函数规模门限、没有候选位置、概率选择和 IR 预算都可能使转换不发生；普通可选 VM 还可能在最终 wrapper 超预算时回滚。编译成功、程序正常输出或存在某个辅助符号，都不能单独证明 VM 已提交。
3. **不同能力的失败行为不同。** 静态混淆通常不做运行时拒绝；独立 AntiDebug 默认让受保护函数提前返回零值；云分发在实际 VM 分发时使用错误 offset，可能触发 trap/非法跳转；最终 ELF 完整性另有加载期校验。不能统一描述成“检测到异常就立即杀进程”。
4. **模块级不等于进程级。** `strenc`、`fmerge`、共享 VM 引擎/表的作用域是当前 LLVM Module，普通分文件编译通常对应一个编译单元，不会自动覆盖其他 `.o`、`.so` 或第三方 SDK。
5. 交付前同时检查编译报告、后链接结果与真实运行。已验证的特定架构/参数组合，不等于所有目标平台、所有 C++ 特性都支持。

## 一、项目定位

本项目是基于 LLVM 的 Android/AArch64 混淆工具链，核心由两部分组成：

- LLVM/Clang/Opt 构建工具链。
- XOLLVM 混淆 Pass 和测试工具。

混淆配置主要通过 C/C++ 函数注解和 `opt`/`clang` 的 `-mllvm` 参数传递。

**组件边界**：`zoneauth` 注解已移除；Zone 登录、卡密、心跳、租约和网络 SDK 由 `../demo/jni/zone_runtime` 集成。编译器仍支持 `vm(cloudDispatch=1)`，它注入运行时外部调用，不自带云服务或授权配置。`docs/obf_annotations.h` 只定义宏，不是运行时库；单独 include 或使用普通 Clang 不会自动开启 XOLLVM Pass。

## 二、混淆功能

当前项目包含以下主要混淆和保护能力：

- VM 虚拟化：把函数转换为内置字节码并由运行时解释执行。
- MBA 混淆：用等价的混合布尔算术表达式改写运算。
- BCF：插入伪控制流和不透明谓词。
- 基本块切分：拆分控制流基本块。
- 指令替换：用更复杂的等价指令序列替换简单操作。
- 控制流扁平化：把函数控制流改造成状态分发器。
- 虚拟调用：通过合成表和间接分发隐藏直接调用关系。
- 语义扩散：把值的计算分散到多个辅助计算槽。
- 常量加密：运行时重建整数和浮点常量。
- 字符串加密：运行时延迟解密字符串字面量。
- 函数合并：把多个函数合并到共享分发体。
- 反反编译：插入干扰反汇编器和反编译器的结构。
- AntiDebug：支持 tracerPid、ptrace、时序、maps、VM 字节码完整性和动态监控；Android/AArch64 可独立开启工具进程、注入库、调试端口、VPN 接口、代理环境变量、iptables 重定向及 SELinux 检测，默认全部关闭。
- Anti-Optimization Shield：降低后续 `-O2/-O3` 优化还原混淆结构的可能性。
- IR 验证和报告：检查每阶段 IR，并生成混淆报告/witness 信息。

## 三、逐项用法、范围和限制

以下示例均以函数定义前放置 `OBF_FN("配置")` 为用法；概率和位置上限只作用于符合条件的候选，`prob=100` 也不表示所有指令都能转换。

| 功能 / 示例配置 | 实际作用与范围 | 使用限制与成本 |
|---|---|---|
| `mba(prob=60,depth=2)` | 当前函数的合适整数算术/位运算改写成等价表达式；默认 `prob=40,depth=3,maxSites=120` | 不加密整个函数或全部浮点计算；深度、项数及 layered 会放大编译时间/IR。`preset=light/medium/high/max` 是 MBA 自己的预设，不能与 VM 预设混淆。SLE/inputZero 提高分析成本，不保证求解器无法还原 |
| `substitution(loop=1,maxSites=40)` / `sub` | 对支持的简单指令做等价序列替换 | 默认 `loop=1,maxSites=0`（自动预算）；不是每类指令都有替换规则；多轮可能膨胀，也可能被后续优化化简 |
| `bcf(prob=30,loop=1)` | 给符合条件的块插入不透明谓词/伪分支 | 默认概率 30；`maxBlocks=0` 为自动策略；EH、特殊控制流及预算可限制转换。假路径不代表业务存在额外分支，也没有联网验证 |
| `split(num=5)` | 将可切分基本块分段，增加 CFG 碎片 | 默认 5；太短的块、PHI/EH/musttail 等不能任意切分；单独使用不隐藏业务语义 |
| `flattening(minBlocks=3,maxBlocks=200)` / `fla` | 当前函数的正常 CFG 改成状态分发结构 | 默认不接受已有间接调用；拒绝 `indirectbr/callbr/musttail/naked`、WinEH funclet 等；Itanium EH 仅处理可用的正常块。**与同一函数的 `vm` 互斥，编译报错** |
| `vcall(prob=30,encTable=1)` | 将当前函数中符合条件的直接调用改成合成表/间接调用 | 不是 VM，也不自动转换 callee 函数体。要求当前模块内有定义，跳过外部声明、intrinsic、函数指针调用、varargs、musttail；`merge=1` 与 `encTable=1` 同开时回退明文合并表；运行时表初始化依赖 ctor |
| `sdiff(prob=45,slots=3,maxSites=80)` | 将合适值的计算分散到多个计算槽 | 只改选中的值，增加临时存储与访存；不是数据流加密或全局内存保护 |
| `constenc(prob=60,encInt=1,encFP=1)` | 将当前函数支持的常量操作数变成运行时重建序列 | 默认 `maxSites=200,minAbs=2`；支持 1–32/64 位整数及 float/double，跳过 switch case、GEP、PHI、alloca 等结构常量、intrinsic/inline asm；不会加密全部 `.rodata`，运行时数值仍可观察 |
| `strenc(cipher=chacha,min=4)` | 模块级扫描合适 C 字符串，函数执行时在局部缓冲区解密 | 默认 **ChaCha20**，可显式选 AES-CTR 或弱 XOR；跳过 `%` 格式串、过短字符串、不可丢弃的外部符号、地址转整数等候选。全局初始化引用可能使原文仍被保留，不能保证 `strings` 完全无明文；解密缓冲区不保留静态字符串的永久地址/生命周期 |
| `fmerge(group=checks,thunk=0)` | 同模块中同组的合适函数合并到选择器分发体 | 至少需要可合并的一组候选；默认 `thunk=0` 只收内部、未被真实取地址的函数，`min=4,max=2000`；拒绝 varargs、EH、inline asm、特殊 ABI 参数等。外部/取地址函数需 `thunk=1`，此时仍保留转发入口，不等于消除 ABI 符号 |
| `adec(prob=50,maxSites=40,strength=2)` | 插入干扰反汇编/反编译的 gadget、间接跳转、诱饵等 | 依赖目标架构；`rdtsc` 技术仅 x86。不是 AntiDebug，不能保证反编译器无法分析。自定义汇编及 clobber 必须匹配实际目标；不适合直接复制另一架构的 gadget |
| `shield(maxSites=200)` / `antiopt` | 插入 volatile/恒等式/DSE/CFG 屏障，降低后续优化消除混淆的可能性 | 不是“禁止一切优化”或防破解证明；增加访存/体积。默认拓扑顺序在主要混淆后、`adec` 前，字符串在注解里的书写顺序不是默认实际执行顺序 |
| `aes_stub(mba(prob=40))` | 对字符串解密存根附加子 Pass，模块级选取配置 | 单独写它不保证存在待解密字符串，也不替代 `strenc`；模块共享存根应保持一份一致配置。`strenc_stub` 当前会作为未知 Pass 被丢弃。字符串 cipher 选择与 VM 的 AES 字节码层是两套配置 |

### 字符串与函数合并的模块级注意事项

- 给一个函数写 `strenc`，可能改写同模块未标注函数使用的字符串。多个字符串配置会合并：`min` 取最大值，ChaCha/AES/keysplit 开关按请求合并，ChaCha 优先；不要依靠不同函数的注解实现逐函数字符串算法隔离。
- 当前字符串路径把函数内使用改到局部解密缓冲区。业务若返回字符串字面量指针、跨调用保存该指针、比较字符串地址或让异步线程继续持有它，应先核对生命周期与生成 IR，不能假定仍具备静态存储期语义。
- `fmerge` 同组配置冲突时，按函数名字典序首项的设置执行并警告；不是每个成员各自采用不同 dispatcher。合并后仍需核对报告，不能假定成员上的所有其他注解都原样作用于原函数边界。

### VM：函数级字节码解释执行

```cpp
OBF_FN("vm(preset=high)")
int protected_math(int x) { return (x * 17 + 23) ^ 0x5a; }

// AArch64 最大预设；最终 ELF 必须进行 targets/audit/seal/verify。
OBF_FN("vm(preset=max,nestedVM=0,budgetMax=40000)")
int critical_math(int x) { return (x * 17 + 23) ^ 0x5a; }
```

`budgetMax=40000` 是特定小函数的配置示例，不是所有函数通用的正确预算。应先看报告再调节；`OBF_FN` 仅防止内联，不保证候选满足 VM 的 IR/ABI 限制。

- 转换后的函数成为 wrapper，准备字节码、寄存器文件与目标表，再调用 VM 引擎。共享引擎只让多个兼容函数复用解释器，不会自动虚拟化未标注函数或它们的整个调用树。
- 普通默认：`encBytecode=1,encDispatch=1,strongBytecode=1,blindTargets=1,obfRegIdx=1,handlerVariants=3,randISA=1,wrapperFamily=split`；`hardened/lazyDecrypt/nestedVM/encodedTargets/whiteboxAES/cloudDispatch/antiDebug` 默认关闭。
- `preset=medium` 采用基础组合；`high` 增加 hardened/threaded/keyed；`max` 增加独立变形引擎、4 个 handler 变体、嵌套 VM、白盒 AES、lazy、常量入流、字段布局、扩展 ISA、最终目标编码等。显式参数覆盖预设。**`max` 不自动开启云分发或独立反调试检测器**，`preset=light` 已移除且会报错。
- `encBytecode=1,lazyDecrypt=0`：加载 ctor 去除整段 AES 外层，不等于内存中永远只有完整密文。`lazyDecrypt=1` 按 16 字节块取指解密，`constInStream=1` 才把支持的常量放进加密流；寄存器 XOR/rolling key 也不隐藏正在 CPU 中使用的数值。
- `encBytecode=0` 会使 `lazyDecrypt/hardened/constInStream` 失效；`whiteboxAES=1` 同时关闭 `encBytecode` 会报错。`hardened` 隐含寄存器加密，不等于开启所有反调试检测器。
- `nestedVM` 只将特定算术/比较等 handler helper 再虚拟化，最多两层，不是递归加壳整个程序；关闭它也会关闭 `nestedVMHardened`。`metamorphicEngines` 需要引擎池大于 1 或 `perFnEngine=1`。
- `bindAntiDebug` 需要 hardened、有效检测来源和 `responseCorrupt=1`；只写 `integrity=1` 或无效权限下的检测器不一定构成来源，应检查 `effective` 与 `disabled_reasons`。它绑定解码盐值，不是恢复白盒 AES 密钥的功能。
- 需求裁剪只发射实际 opcode/语义需求；96 个逻辑 opcode 的指令集不表示每个引擎都包含 96 个 handler。变体、诱饵、独立引擎和白盒表都会增加成本；白盒表每实例 372736 字节，多个 caller/内层实例会累计。

#### VM 输入与平台限制

- 适合边界清楚的整数、指针、float/double 计算及受支持的普通 C ABI 调用。`EH/invoke`、`musttail`、`callbr`、已有 `indirectbr`、`naked` 会被拒绝；其他未支持 IR/intrinsic、特殊调用 ABI/聚合参数、寄存器文件超容量也会导致跳过或 strict 失败。CALL 最多 16 个显式实参；不能据此推断任意 C++ STL/异常代码都可 VM 化。
- i1 的比较/分支有支持，但不等于所有 i1 内存槽均受支持；`-O0` 下返回 bool 的代码可能产生不支持的 load/store i1。vector/聚合值、特殊原子操作等应以发射器和报告为准，不在这里宣称通用支持。
- `llvm.fmuladd/fma/fabs/minnum/maxnum/copysign` 当前不会被不等价降级为普通运算。测试基础乘加可用 `-ffp-contract=off` 避免生成融合 intrinsic，但这**不等于实现了 fma 语义**，也不能用 fast-math 结果代替严格浮点等价验收。
- `encodedTargets=1`（max 默认包含）要求 **AArch64 little-endian ELF64，交付路径为 PIE**；最终目标表需后链接工具回填。ARM32 直接用 `vm(preset=max)` 会被拒绝。已验收的 ARM32 配置为 `vm(preset=max,encodedTargets=0,nestedVM=0)` 等支持子集，FP 用 `-ffp-contract=off`；这不是完整 max 或全部架构支持声明。
- 静态逆解公开 descriptor 能恢复 handler/engine 目标；白盒 AES 与加密字节码均不是“无法提取”的保证。动态白盒字节码提取适配器尚未实现，攻击工具输出 `UNSUPPORTED` 不能作为防护成功结论。

### 云 VM：什么时候会终止，什么时候不会

```cpp
OBF_FN("vm(preset=max,nestedVM=0,cloudDispatch=1,budgetMax=40000)")
int cloud_protected_math(int x) { return (x * 17 + 23) ^ 0x5a; }
```

此例还必须链接提供 `__zone_get_dispatch_offset()` 的真实运行时、SDK 及依赖，初始化并完成服务端要求的登录/心跳/capability。只复制注解头、把函数名改为 auth、或者使用 `preset=max`，都不会自动集成这些步骤。

真实执行链：

```text
进入开启 cloudDispatch 且已提交的 VM 函数
  → 在中央或 threaded handler 分发处调用 __zone_get_dispatch_offset()
  → handler 索引 + offset
  → 合法云值对应 offset=0，正常分发
  → 错误 offset 可能导致越界/错误 handler/陷阱
  → 当前 encodedTargets 产物越界时触发边界检查 brk（SIGTRAP）
  → 未被处理的致命信号终止整个进程，而不是只终止该函数
```

**触发范围：**

| 场景 | 当前行为 |
|---|---|
| 已断网，但当前窗口的缓存云值仍有效 | 不保证立即失败；断网事件本身不是终止条件 |
| 云值过期，带云分发的 VM 正在继续执行 | 后续实际 handler 分发使用失效 offset，可在本次调用内失败；不必等下一次函数调用 |
| 云值过期，VM 正在某个原生外部调用中阻塞 | 在返回 VM、继续分发之前，没有新的 handler 索引计算 |
| 云值过期，程序只执行普通原生函数、非云 VM 或等待输入 | 不会仅凭云值过期自动发生这条分发越界；当前后台更新器没有“到期立即结束进程”动作 |
| 尚未执行失效 VM，先恢复网络再进入 VM | 当前运行时会尝试同步刷新；成功取得当前窗口 V 后可能正常执行。这不是崩溃恢复功能 |
| 已触发致命 trap，进程已经结束 | 原进程不能靠恢复网络继续；验收中的 recovery 与 expiry 是不同进程 |

当前运行时按服务器校准时间计算 `window=floor(timestamp/60)`，预取间隔默认 50 秒；首次/跨窗口分发会同步刷新，失败后用旧 V 与**当前**窗口计算 HMAC，再 `& 0xFFF`。因此不能承诺“断网后固定 60 秒整准时终止”，实际还依赖窗口位置、请求耗时、线程调度和是否执行到云分发。

**概率边界也要明确：** 截断 HMAC 不是确定性的过期布尔标志。对于不匹配的 V/window，offset 通常非零，但理想均匀模型下仍约有 `1/4096` 的零值碰撞；非零也不保证每个原索引相加后立刻越界，可能先命中表内其他记录。当前严格验收要求实际证明 offset 非零、真实索引越界及故障归因，不能把“理论应该崩”计为通过。12-bit 掩码也不是云授权密钥的安全位数；增大掩码会增加服务端搜索成本，不等于完整授权安全性证明。

所以，当前能力的准确名称是：**函数级 VM 的云值分发依赖**。它没有实现“无论业务正在执行什么，断网/云值过期后整个进程必在固定时间内停止”的进程级持续看门狗。

### Android/AArch64 AntiDebug

- 新增开关：`debuggerProcess`、`injection`、`debugPorts`、`vpn`、`proxy`、`iptables`、`selinux`，仅在 Android/AArch64 发射。
- `rootRequired=0`（默认）：跳过 `debuggerProcess` 和 `iptables`；其余检测读取失败时跳过。
- `rootRequired=1`：入口及后台先检查有效 UID；不是 root 时直接触发响应，不执行特权探测。启用项读取失败或解析异常也触发响应；该选项不自动启用检测器。
- `dynamic=1` 按有效配置复用监控线程，异常锁存；不同配置及同步/动态状态独立。退出时停止并回收线程。
- `proxy` 检查大小写代理环境变量，不涵盖 Android 系统代理设置；VPN 根据接口名前缀和编号识别；调试端口仅检查本机 IPv4 的 23946、23947、27042。
- `ptrace` 兼容为只读 TracerPid 检测，入口与后台均可使用，不改变跟踪或信号关系；`integrity` 与 VM 组合后仅在初始化时检查字节码。监控创建失败锁存，退出时回收线程。
- JSON `anti_debug` 记录请求配置，包括完整 `detectors` 和 `root_required`；实际发射受目标与权限策略限制。VM 引擎分组键也包含新增字段。

```cpp
OBF("antidebug(tracerPid=1,injection=1,dynamic=1,interval=250)")
int protected_check(int x) { return x + 9; }

OBF("antidebug(rootRequired=1,debuggerProcess=1,iptables=1,selinux=1)")
int root_check(int x) { return x + 9; }
```

默认响应为函数提前返回对应类型零值（void 则直接返回）；**零值不一定是你的业务失败值**，例如“返回 0 表示验签成功”的 API 不能直接把它当作安全失败。调用者需要按实际接口语义处理。

`responseCorrupt=0` 仅记录状态。`dynamic=1` 后台锁存检测结果，不是通用的异步 kill：独立入口 guard 在后续进入该函数时消费状态，VM salt 绑定则在对应执行路径消费；不会自动打断任意未保护函数。异常锁存后不会因调试器离开而自动清零。VM `integrity` 是初始化时的字节码检查，不是每次 handler 分发都重新哈希；最终 ELF manifest 的加载期完整性是另一项能力。`timing` 阈值受负载/调度影响，应实测误判。

### VM 引擎需求裁剪（demand pruning）

- 引擎只发射被实际用到的 handler；superOps 开启时保留整组融合 opcode。
- dispatch 去掉 `urem` 钳制，改为显式 `icmp uge <OP_COUNT>` 域检查 + trap；
  ICMP 改为显式谓词块 `vm.ic.<pred>` + trapping 默认；invalid 块统一
  `llvm.trap()+unreachable`。
- 引擎分组：不同配置（如不同 randISA）不再被合并到同一引擎，冲突时分配独立
  EngineId。

### 若干修复

- `threadedDispatch`：未使用的占位 handler 块补 `unreachable`，修复验证器
  "Basic Block 无终结符"/崩溃。
- `vm + antidebug`：默认让 standalone AntiDebugPass 排在 VM 之后，避免多值返回
  导致 VM 被跳过。
- `hardened` 包装展平：展平前对跨块值做 reg2mem，修复支配性违规引发的 LICM 崩溃。

## 四、注解、预设、顺序与预算

引入头文件：

```cpp
#include "obf_annotations.h"
```

给函数添加混淆配置：

```cpp
OBF("vm(hardened=1), mba, bcf")
int secret_check(const char* value) {
    return value != nullptr;
}
```

常用预设：

```cpp
OBF_MINIMAL
OBF_BALANCED
OBF_AGGRESSIVE
OBF_VM
OBF_VM_HARDENED
OBF_STRINGS
OBF_FLATTEN
OBF_CONSTENC
OBF_FMERGE
```

`OBF_FN(spec)` 与 `OBF(spec)` 类似，但额外添加 `noinline`，适合需要保持函数边界的小函数。

**现有 `OBF_MAX` 宏的已知限制：** 当前定义同时包含 `vm(preset=max)` 和 `flattening`，会被流水线的互斥检查拒绝；这份使用文档不改变宏行为。需要最大 VM 时写 `OBF_FN("vm(preset=max)")`，再按实际需要增加兼容 Pass，不要直接采用该旧宏。`OBF_SENSITIVE("region")` 则包含 strict sensitive 和 max VM，也有后链接和架构要求。

- Pass 名称规范化、别名和参数 key 的处理并不完全相同；按参考头的拼写使用 key。VM 布尔参数只接受 `0/1/true/false`；不能泛称所有 Pass 都接受 `yes/on`。未知 Pass 会警告并被丢弃，未知 key 在不少 Pass 中被忽略（sensitive 等另有严格校验），因此拼错参数可能仍编译成功。
- 预算写在已识别的 Pass 括号内，例如 `vm(budgetMultiplier=12,budgetMax=40000)`；不要单独写成 `OBF("budgetMax=40000,vm")`。
- 全局预算默认 multiplier=50、hard cap=0；每函数非零覆盖优先。一般预算有 256 条 IR 的最低基线再受 hard cap 限制；预算按 IR 指令计，不是 ELF 字节数、运行时指令数或安全等级。每函数注解值 0 表示沿用全局，不是单独取消全局限制；全局 multiplier=0 才关闭预算追踪。
- 提高 multiplier 可能让前置 MBA/BCF 膨胀到 VM 寄存器文件超容量；提高 `budgetMax` 也不增加寄存器容量。先查看 `skip_reason`，再调一个明确的限制。
- 注解默认按拓扑依赖排序，`fmerge/strenc` 在模块阶段运行；`sensitive` 检查原始边界，VM 之前的算术/CFG 转换也会影响 VM 成本，独立 AntiDebug 在 VM 后插入 guard。`vm+flattening` 是显式冲突，强制 CLI 顺序也不能解除。不要把注解列表理解成手写命令流水线。

### sensitive：把判断与动作收进同一保护边界

```cpp
extern int verify_signature(const unsigned char*, unsigned long);
extern void allow_action();
extern void deny_action();

OBF_FN("sensitive(region=auth,strict=1),vm(preset=max,nestedVM=0)")
void verify_and_act(const unsigned char* data, unsigned long size) {
    int verdict = verify_signature(data, size);
    if (verdict == 1) {
        allow_action();
    } else {
        deny_action();
    }
}
```

当前分析以可识别的外部非 void 调用结果为敏感来源，跟踪派生值/局部存储，要求在区域内形成成功失败分支，不允许结果经 return、外部 store、未知调用或 inline asm 逃逸。只写 `return verify_signature(...)` 不是完整敏感边界。`region` 只是诊断标识，strict=1 不满足边界或 VM 无法提交则编译失败；strict=0 不提供同样的失败即停止保证。它不是自动发现所有业务授权点或证明授权逻辑本身正确，也不会自动开启云分发。

### 报告应检查什么

- `-obf-verify` 只验证 LLVM IR 结构，不证明业务输出一致、云授权有效或抗逆向能力。
- `-obf-report-json=文件` 中，按目标函数检查 `passes` 的 ran/skipped、`skip_reason`；VM 必须 `phase=committed`，再检查 `requested/effective/disabled_reasons`。完整 Clang 流程可能有多条 VM pass 记录，应拒绝其中任一 skip，而不是只取第一条 ran。
- `post_link=pending` 是编译阶段待处理状态，不能冒充最终 ELF 已加固；还要验证 descriptor、seal 和交付文件 hash。
- `-obf-no-skips` 可将已报告的跳过升级为失败，适合验收，但不是“所有候选全部改写”开关；无候选的模块级 Pass 仍需看实际输出。

## 六、基本混淆流程

以下在业务目录执行，已有 `input.c` 并包含注解头。显式指定 Android triple 与 NDK sysroot；示例为 AArch64/API 26。C++ 源码改用 `clang++`/`-std=c++20`，最终使用 NDK `clang++ -static-libstdc++` 链接。

先把源文件编译为 LLVM IR：

```bash
TOOLS="/data/user/0/com.termux/files/home/xollvm-android/build-sensitive/bin"
NDK_HOST="/data/user/0/com.termux/files/home/android-ndk-r30-ollvm-r23-beta3/toolchains/llvm/prebuilt/linux-arm64"
"$TOOLS/clang" --target=aarch64-linux-android26 --sysroot="$NDK_HOST/sysroot" -I"/data/user/0/com.termux/files/home/xollvm-android/xollvm/docs" -O0 -Xclang -disable-O0-optnone -S -emit-llvm input.c -o input.ll
```

运行混淆 Pass：

```bash
"$TOOLS/opt" -passes=obfuscation -obf-seed=1 -obf-verify -obf-report-json=obf-report.json -S input.ll -o output.ll
```

把混淆后的 IR 编译为对象并完成最终链接（此示例未包含云运行时，因此不能直接链接 cloudDispatch 对象）：

```bash
"$NDK_HOST/bin/clang" --target=aarch64-linux-android26 -O2 -c output.ll -o output.o
XOLLVM_LINK_COMPILER="$NDK_HOST/bin/clang++" XOLLVM_ELF_HARDENER="$TOOLS/xollvm-elf-hardener" bash "/data/user/0/com.termux/files/home/xollvm-android/xollvm/tools/xollvm-link" --target=aarch64-linux-android26 -static-libstdc++ -Wl,--rosegment output.o -ldl -pthread -lm -o output
```

常用全局参数：

```text
-obf-seed=N
-obf-deterministic
-obf-verbose
-obf-verify
-obf-max-function-insts=N
-obf-max-function-blocks=N
-obf-ir-budget-multiplier=N
-obf-ir-budget-max=N
-obf-report-json=文件
-obf-no-skips
-obf-pipeline-ordering="mba,split,bcf"
```

源码直接走混淆 Clang 时，另外需要 `-mllvm -enable-obfuscation`，每个混淆选项分别用 `-mllvm` 传入；普通 `opt` 则通过 `-passes=obfuscation` 启用。不要让同一份已混淆 IR 再走源码注解流水线重复处理，除非明确需要并重新验收。

### 最终 ELF 后链接与完整性

- 正式入口顺序：`link → targets → audit → seal → verify → 原子替换输出`。`xollvm-link` 用于链接对象，不是编译入口；demo NDK wrapper 对编译和链接分别转发。缺工具/后处理失败不得继续交付新输出。
- `targets` 回填 handler/engine descriptor，并处理 Android 重定位；不能拿未处理的 encodedTargets ELF 直接运行。`audit` 检查包括可执行零洞等策略，**不等于发现所有安全缺陷**。
- strict sensitive 会生成 manifest 占位与运行时 ctor；`seal` 回填摘要和范围。摘要覆盖 manifest（摘要窗口清零）、ELF header/程序头及文件支持的可执行 PT_LOAD。没有 manifest 的 targets-only ELF 可被 verify 验收，但不因此获得相同的运行时加载完整性保护。
- 不是整个磁盘文件、所有只读/可写数据、外部库和运行中每条指令的持续校验。文件尾追加内容由包签名等负责。动态导入名仍可能在 `.dynsym` 可见。
- strip/objcopy/修改或重链接放在最终 targets/audit/seal/verify **之前**；交付的必须是最后 verify 的那份文件。seal 后改变被覆盖字节会使摘要失效，不能仅以程序仍可启动判通过。

## 八、`docs/obf_annotations.h` 文件分析

### 文件用途

`docs/obf_annotations.h` 是给业务项目使用的独立注解头文件。它把 XOLLVM 的混淆配置封装成宏，让业务代码可以按函数指定混淆 Pass，而不需要直接手写 LLVM 注解字符串。

它不是混淆器实现，也不是运行时库，不能单独完成混淆。真正读取这些注解的是项目中的 annotation parser 和 Obfuscation Pipeline。

### 宏展开

在 Clang 下：

```cpp
OBF("mba, bcf")
```

会展开为类似：

```cpp
__attribute__((annotate("obf: mba, bcf")))
```

`OBF_FN` 会额外添加 `noinline`。在 GCC/MSVC 等非 Clang 编译器下，这些宏展开为空，因此同一份业务源码仍可编译，但不会应用 XOLLVM 混淆。

### 配置内容

文件主要记录三类内容：

- `OBF`、`OBF_FN` 核心宏。
- `OBF_MINIMAL`、`OBF_BALANCED`、`OBF_AGGRESSIVE` 等预设，以及带已知组合冲突的旧 `OBF_MAX` 定义。
- 每个 Pass 的名称、别名、参数范围、默认值和示例。

覆盖的配置包括 `mba`、`constenc`、`bcf`、`split`、`substitution`、`flattening`、`vcall`、`sdiff`、`strenc`、`fmerge`、`adec`、`antidebug`、`shield`、`sensitive` 和 `vm`，并说明云运行时与最终 ELF 工具的边界。

文件还列出了只能通过 `opt`/`clang` 命令行传入的全局参数，例如 `-obf-seed`、`-obf-verify` 和 `-obf-pipeline-ordering`。这些参数不是 `OBF()` 注解的一部分。

### 使用注意事项

- 注解只影响带注解的函数，但 `strenc`、`fmerge`、`vm` 等部分能力可能是模块级行为，具体以文件中的 Pass 说明为准。
- `OBF_FN` 的 `noinline` 可以防止函数被内联到未注解调用者，从而保持按函数混淆的边界。
- 最大 VM/独立引擎/白盒/嵌套的成本需要按真实函数测量；旧 `OBF_MAX` 组合冲突见第四节。
- `shield` 默认在主要混淆后、`adec` 前；`OBF_AGGRESSIVE` 已包含它。
