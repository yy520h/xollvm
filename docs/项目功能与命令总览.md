# XOLLVM 项目功能与命令总览

本文档汇总当前项目已有功能、Zone 授权功能、常用构建/测试命令，以及 `docs/obf_annotations.h` 的用途。

## 一、项目定位

本项目是基于 LLVM 的 Android/AArch64 混淆工具链，核心由两部分组成：

- LLVM/Clang/Opt 构建工具链。
- XOLLVM 混淆 Pass、运行时和测试工具。

混淆配置主要通过 C/C++ 函数注解和 `opt`/`clang` 的 `-mllvm` 参数传递。

## 二、原有混淆功能

当前项目包含以下主要混淆和保护能力：

- VM 虚拟化：把函数转换为内置字节码并由运行时解释执行。
- MBA 混淆：用等价的混合布尔算术表达式改写运算。
- BCF：插入伪控制流和不透明谓词。
- 基本块切分：拆分控制流基本块。
- 指令替换：用更复杂的等价指令序列替换简单操作。
- 控制流扁平化：把函数控制流改造成状态分发器。
- 虚拟调用：通过合成表和间接分发隐藏直接调用关系。
- 语义扩散：把值的计算分散到多个辅助计算槽。
- 常量加密：运行时重建整数和浮点常量。
- 字符串加密：运行时延迟解密字符串字面量。
- 函数合并：把多个函数合并到共享分发体。
- 反反编译：插入干扰反汇编器和反编译器的结构。
- AntiDebug：支持 tracerPid、ptrace、时序、maps、完整性和动态监控检测。
- Anti-Optimization Shield：降低后续 `-O2/-O3` 优化还原混淆结构的可能性。
- IR 验证和报告：检查每阶段 IR，并生成混淆报告/witness 信息。

## 三、本轮新增/加固能力

### 云值驱动 VM dispatch（`cloudDispatch`）

- VM 注解新增开关 `vm(cloudDispatch=1)`：在两处 dispatch（中央循环与 threaded）
  注入对 `__zone_get_dispatch_offset()` 的调用，把云值 V 派生的偏移叠加到
  handler 表索引上。
- 合法 V → 偏移为 0 → 正常执行；V 过期/缺失/被篡改 → 偏移非 0 → 索引越界或
  命中陷阱自然崩溃。本地零校验，没有可被 NOP 的 `if (有效)/if (未过期)` 分支。
- 默认关闭时输出与非云构建一致（不引用运行时符号）。
- 客户端运行时见 `zone_runtime/cloud_value_manager.{h,cpp}`：按 `window_id`
  分桶、手写 HMAC-SHA256 派生偏移，首次 dispatch 同步拉取 V（避免首跑必崩），
  之后按预取间隔异步刷新。
- 云端参考实现 `zone_runtime/cloud/capability_v1.js`：为每个 window 搜索 V 使
  `HMAC(V, window) & MASK == 0`，随响应下发 `dispatch_v`/`window_id`。
- 约定：客户端 `VM_DISPATCH_OFFSET_MASK` 必须等于云端 `dispatchOffsetMask`，
  当前为 12-bit（`0xFFF`）。

### VM 引擎需求裁剪（demand pruning）

- 引擎只发射被实际用到的 handler；superOps 开启时保留整组融合 opcode。
- dispatch 去掉 `urem` 钳制，改为显式 `icmp uge <OP_COUNT>` 域检查 + trap；
  ICMP 改为显式谓词块 `vm.ic.<pred>` + trapping 默认；invalid 块统一
  `llvm.trap()+unreachable`。
- 引擎分组：不同配置（如不同 randISA）不再被合并到同一引擎，冲突时分配独立
  EngineId。

### 若干修复

- `threadedDispatch`：未使用的占位 handler 块补 `unreachable`，修复验证器
  “Basic Block 无终结符”/崩溃。
- `vm + antidebug`：默认让 standalone AntiDebugPass 排在 VM 之后，避免多值返回
  导致 VM 被跳过。
- `hardened` 包装展平：展平前对跨块值做 reg2mem，修复支配性违规引发的 LICM 崩溃。
- cloudDispatch 端到端修复：云函数入口改为 `exports.<fn> = async (event,context)`；
  客户端补赋 `window_id`/`dispatch_blob`/`dispatch_v`（否则验签失败）；capability
  状态默认路径改为可写目录。

## 四、源码注解功能

引入头文件：

```cpp
#include "obf_annotations.h"
```

给函数添加混淆配置：

```cpp
OBF("vm(hardened=1), mba, bcf")
int secret_check(const char* value) {
    return value != nullptr;
}
```

常用预设：

```cpp
OBF_MINIMAL
OBF_BALANCED
OBF_AGGRESSIVE
OBF_MAX
OBF_VM
OBF_VM_HARDENED
OBF_STRINGS
OBF_FLATTEN
OBF_CONSTENC
OBF_FMERGE
```

`OBF_FN(spec)` 与 `OBF(spec)` 类似，但额外添加 `noinline`，适合需要保持函数边界的小函数。

## 六、基本混淆流程

先把源文件编译为 LLVM IR：

```bash
"/data/user/0/com.termux/files/home/xollvm-android/build/bin/clang" -O0 -Xclang -disable-O0-optnone -S -emit-llvm input.c -o input.ll
```

运行混淆 Pass：

```bash
"/data/user/0/com.termux/files/home/xollvm-android/build/bin/opt" -passes=obfuscation -obf-seed=1 -obf-verify -S input.ll -o output.ll
```

把混淆后的 IR 编译为目标程序：

```bash
"/data/user/0/com.termux/files/home/xollvm-android/build/bin/clang" output.ll -o output
```

常用全局参数：

```text
-obf-seed=N
-obf-deterministic
-obf-verbose
-obf-verify
-obf-max-function-insts=N
-obf-ir-budget-multiplier=N
-obf-pipeline-ordering="mba,split,bcf"
```

## 七、Zone 授权功能

Zone 功能由 `zone_runtime/zone_wrapper.cpp` 和项目内置官方 SDK 提供。LLVM Pass 只在实际启用 Zone 时注入 C ABI 调用和链接 marker；使用项目提供的 `xollvm-zone-clang` 作为最终编译/链接入口时，构建程序根据 marker 逐项检测 curl、zlib、libssl、libcrypto，兼容时复用目标库，缺失或 ABI 不兼容时加入经过符号隔离的 Zone 私有库。未启用 Zone 的目标不会自动加入这些依赖。bundled 与 external 模式不能混用，external 模式必须显式提供并校验四个 archive。

编译器侧参数：

```text
-mllvm -obf-zone-enable
-mllvm -obf-zone-software-id=<software-id>
-mllvm -obf-zone-version=<software-version>
-mllvm -obf-zone-encrypt-key=<client-key>
-mllvm -obf-zone-encrypt-iv=<client-iv>
-mllvm -obf-zone-algorithm=<algorithm-name>
-mllvm -obf-zone-heartbeat-period=120
-mllvm -obf-zone-offline-grace=180
```

卡密不写入注解，也不写入编译器参数。目标程序在运行时读取卡密并执行：

1. 初始化 `ZoneHelper`。
2. 调用 `LoginC` 登录卡密。
3. 调用 `HeartBeat` 维持租约。
4. 调用 `GetAntiAlgorithmValue` 获取云算法结果。
5. 通过 `xollvm_zone_require` 检查能力。
6. 只有在 `xollvm_zone_shutdown()` 阶段调用 `Logout`。

心跳返回码需要按官方 SDK 的业务协议解释：`50010` 表示卡密/账号心跳，`50090` 表示游客试用心跳。后台记录中的“执行结果成功”表示云函数执行成功，不能仅因为请求类型显示为心跳或原因字段显示 `HeartBeat!` 就判定云函数失败。

### Logout 生命周期

`Logout` 不会在登录成功后调用，也不会在首次心跳或云算法完成后调用。当前退出顺序是：

```text
xollvm_zone_shutdown()
  -> 停止心跳线程
  -> 调用 ZoneHelper::Logout()
  -> 清理授权状态
  -> 释放 ZoneHelper
```

正常退出会立即通知服务端。异常崩溃或强制杀进程时无法保证执行退出请求，服务端仍会通过心跳超时清理会话。

### 云值驱动 dispatch 的运行时开关

客户端运行时（`zone_runtime/zone_wrapper.cpp`）支持以下环境变量：

```text
XOLLVM_ZONE_CAPABILITY_OPERATION       能力名（默认 demo_sensitive_action）
XOLLVM_ZONE_CAPABILITY_PUBLIC_KEY      capability 验签公钥（PEM）
XOLLVM_ZONE_CAPABILITY_CODE_MANIFEST   代码清单（默认 demo-code-manifest-v1）
XOLLVM_ZONE_CAPABILITY_BUILD_ID        构建号（默认 demo-build-v1）
XOLLVM_ZONE_CAPABILITY_STATE_PATH      验证状态文件路径
                                       （默认 $HOME/xollvm_zone_capability.state，
                                        其次 $TMPDIR，最后 /data/local/tmp）
```

生成的公钥必须与云端脚本 `signingPrivateKey` 配对，否则 capability 验签失败。

## 九、`docs/obf_annotations.h` 文件分析

### 文件用途

`docs/obf_annotations.h` 是给业务项目使用的独立注解头文件。它把 XOLLVM 的混淆配置封装成宏，让业务代码可以按函数指定混淆 Pass，而不需要直接手写 LLVM 注解字符串。

它不是混淆器实现，也不是运行时库，不能单独完成混淆。真正读取这些注解的是项目中的 annotation parser 和 Obfuscation Pipeline。

### 宏展开

在 Clang 下：

```cpp
OBF("mba, bcf")
```

会展开为类似：

```cpp
__attribute__((annotate("obf: mba, bcf")))
```

`OBF_FN` 会额外添加 `noinline`。在 GCC/MSVC 等非 Clang 编译器下，这些宏展开为空，因此同一份业务源码仍可编译，但不会应用 XOLLVM 混淆。

### 配置内容

文件主要记录三类内容：

- `OBF`、`OBF_FN` 核心宏。
- `OBF_MINIMAL`、`OBF_BALANCED`、`OBF_AGGRESSIVE`、`OBF_MAX` 等预设。
- 每个 Pass 的名称、别名、参数范围、默认值和示例。

覆盖的 Pass 包括 `mba`、`constenc`、`bcf`、`split`、`substitution`、`flattening`、`vcall`、`sdiff`、`strenc`、`fmerge`、`adec`、`shield` 和 `vm`。

文件还列出了只能通过 `opt`/`clang` 命令行传入的全局参数，例如 `-obf-seed`、`-obf-verify` 和 `-obf-pipeline-ordering`。这些参数不是 `OBF()` 注解的一部分。

### 使用注意事项

- 注解只影响带注解的函数，但 `strenc`、`fmerge`、`vm` 等部分能力可能是模块级行为，具体以文件中的 Pass 说明为准。
- `OBF_FN` 的 `noinline` 可以防止函数被内联到未注解调用者，从而保持按函数混淆的边界。
- `OBF_MAX` 体积和运行时开销最大，不应默认用于所有函数。
- `shield` 应放在混淆链后部；`OBF_AGGRESSIVE` 和 `OBF_MAX` 已包含它。
- `zoneauth` 不是普通的静态混淆 Pass，它会注入运行时授权调用，需要最终目标链接 `zone_runtime` 和官方 Zone SDK。
- Zone 卡密不应写入注解字符串、源码、命令历史或仓库。

## 十、敏感信息和构建目录

- 卡密、客户端加密 Key、加密 IV、Token 不应写入 Markdown、源码或 Git。
- `build/` 和其他构建中间目录不应提交。
- 交付到 MT 等环境的可执行文件应注意 C++ runtime 静态链接要求。
- 真实 Zone 测试使用过的卡密应在测试完成后按后台策略回收或更换。
